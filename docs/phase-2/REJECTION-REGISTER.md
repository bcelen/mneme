# Rejected-Alternative Register

**Status:** Accepted
**Review date:** 2026-09-17

No scored candidate is rejected. The records below are alternatives screened out of this evaluation round because their declared boundary conflicts with accepted requirements or adds an unproved service without a demonstrated need. “Screened out” is not a permanent ban; each record has a revisit trigger.

| ID | Alternative boundary and evidence reviewed | Reason screened out / affected gates | Consequence | Revisit trigger |
|---|---|---|---|---|
| REJ-001 | Public multi-user SaaS with provider-hosted source, indexes, AI, and administration. Accepted privacy, export, and single-user requirements reviewed. | Conflicts with default-private scope and creates unresolved G-06/G-08/G-10 issues. | Hosted collaboration features are excluded. | User explicitly proposes multi-user/public scope and approves privacy, service, cost, and exit changes. |
| REJ-002 | Provider-resident search over live Gmail/Outlook accounts, with no complete local source archive. Provider export evidence reviewed. | Cannot satisfy G-01–G-03, G-07–G-08 or the immutable local system of record. | Mneme will not depend on live provider access for preservation or Find. | No revisit without changing accepted preservation principles. |
| REJ-003 | Vector database or model retrieval as the only Find system. NIST/OWASP and accepted Find/Ask boundary reviewed. | Fails deterministic, explainable Find and risks G-03/G-04/G-06/G-10. | Embeddings, if later justified, may only supplement Ask as rebuildable derived data. | Synthetic research tasks demonstrate a lexical/structured gap and a separate ADR satisfies privacy/provenance. |
| REJ-004 | Desktop-only Electron, Tauri, or native Mac application with no credible iPhone/iPad client. Product requirements reviewed. | Fails G-10 and STF-06 target-device scope. | Desktop-shell candidates are not scored in this round. | User changes the target-device requirement or a complete mobile boundary is added. |
| REJ-005 | Dedicated Elasticsearch/OpenSearch-style search cluster added to any candidate. SQLite/PostgreSQL native search evidence reviewed. | No current corpus evidence justifies another stateful service; weakens STF-08/STF-11 and adds G-07/G-09 burden. | Native database FTS is evaluated first. | Synthetic scale, language, or query evidence demonstrates native FTS cannot meet approved budgets. |
| REJ-006 | Client-only archive copies independently stored on every Mac/iPhone/iPad. Preservation and WebKit cache evidence reviewed. | Multiplies sensitive copies, synchronization conflicts, backup scope, and lost-device exposure; weakens G-06/G-07. | Clients use bounded disposable derived caches only. | A separately reviewed offline requirement justifies a secure, auditable replica protocol. |
| REJ-007 | `CAND-001` with PostgreSQL substituted for SQLite. Same Django boundary, but a separate database service materially changes storage and operations. | Not rejected on merit; deferred to avoid silently mutating a scored candidate and because current scale evidence does not require it. | SQLite and PostgreSQL tradeoffs stay visible. | UNC-001/002 or synthetic tests show SQLite cannot satisfy workload/recovery budgets. |
| REJ-008 | `CAND-002` with SQLite substituted for PostgreSQL. Same Next.js boundary, but embedded persistence materially changes worker/concurrency and deployment assumptions. | Deferred as a distinct material variant; it does not add a new client/runtime hypothesis beyond CAND-001's minimal-store comparison. | Candidate count remains reviewable. | Next.js becomes preferred on UX grounds and PostgreSQL is shown disproportionate. |
| REJ-009 | Additional mature server-rendered monoliths with the same browser/embedded-store architecture as CAND-001. | Not individually scored because they do not test a distinct architecture category in this round; framework familiarity is not evidence. | CAND-001 acts as the representative archetype, not a claim that alternatives are inferior. | A proposed framework shows a materially different gate, maintenance, licensing, or source-format outcome. |

Permanent rejection triggers for any candidate are source-archive mutation, outbound mail as a required feature, public exposure as a requirement, unapproved external transfer, application-dependent source interpretation, parser archive-write/credential/network privilege, fabricated lineage, or inability to restore from independently verified preservation evidence.
